
**SocketUp** — дипломный backend-проект Telegram-like мессенджера с потенциалом роста в production-систему. Проект ориентирован на обычных пользователей, команды, компании и сообщества. Текущая кодовая база уже содержит основу для GraphQL/gRPC/WebSocket-архитектуры, а этот README фиксирует текущее состояние репозитория, целевое видение продукта и полное ТЗ для дальнейшей разработки.

---

## 1. Product Summary

### 1.1. Что такое SocketUp
SocketUp — это универсальный мессенджер в духе Telegram, который должен поддерживать:
- личные чаты;
- групповые чаты;
- каналы;
- текстовые сообщения;
- вложения и файлы;
- голосовые сообщения;
- видеосообщения («кружочки»);
- аудио- и видеозвонки;
- realtime-доставку событий;
- поиск по пользователям и сообщениям внутри чата;
- настройки приватности;
- административные механизмы управления платформой.

### 1.2. Цели проекта
- Создать качественный дипломный проект с реальной инженерной архитектурой.
- Получить основу для дальнейшего роста в production-grade продукт.
- Построить backend, который можно расширять мобильным клиентом, web-клиентом и административной панелью.

### 1.3. Целевая аудитория
- обычные пользователи;
- команды и небольшие рабочие группы;
- компании;
- сообщества и контент-авторы.

## 2. Текущее состояние репозитория

### 2.1. Что уже есть
В репозитории уже заложена многосервисная backend-архитектура:
- **FastAPI + GraphQL gateway** — входной API-слой;
- **gRPC backend services** — бизнес-логика пользователей, аутентификации и чатов;
- **WebSocket service** — realtime-доставка событий;
- **PostgreSQL** — основная БД;
- **Redis** — кэш / presence / offline queue / realtime вспомогательные сценарии;
- **MinIO / S3-compatible storage** — целевое хранилище файлов и медиа.

### 2.2. Что реализовано частично
На уровне кодовой базы уже присутствуют:
- схемы пользователей, чатов, участников, сообщений, реакций, контактов и приватности;
- Alembic migration начальной схемы БД;
- gRPC-сервисы для auth / user / chat;
- GraphQL-домены для auth / user / chat;
- WebSocket-обработчики для realtime сообщений и typing events.

### 2.3. Что ещё требует доработки
Проект находится в фазе активной инженерной сборки. Для полной готовности нужно:
- довести документацию и сценарии запуска;
- унифицировать архитектурные слои;

- реализовать недостающие модули;
- покрыть систему тестами;
- формализовать продуктовые требования и roadmap.

## 3. Архитектурное видение

### 3.1. Выбранная архитектура
Для проекта фиксируется следующая архитектура:

- **FastAPI** — API gateway и HTTP entrypoint;
- **GraphQL** — основной прикладной API для клиентов;
- **gRPC** — внутреннее взаимодействие между backend-компонентами;
- **WebSocket** — realtime-коммуникация;
- **Redis** — presence, очереди событий, временные данные;
- **PostgreSQL** — основная реляционная БД;
- **MinIO** — хранение файлов, изображений, видео, аудио и голосовых сообщений.

### 3.2. Основные backend-модули
Планируемая архитектура проекта состоит из следующих блоков:

1. **API Gateway**
   - авторизация запросов;
   - GraphQL endpoint;
   - маршрутизация к внутренним сервисам.

2. **Auth Service**
   - регистрация;
   - логин;
   - refresh token flow;
   - управление сессиями;
   - email verification.

3. **User Service**
   - профиль пользователя;
   - username;
   - настройки приватности;
   - поиск пользователей.

4. **Chat Service**
   - личные чаты;
   - группы;
   - каналы;
   - участники и роли;
   - сообщения;
   - pinned messages;
   - read/delivery state.

5. **Realtime Service**
   - websocket-сессии;
   - typing events;
   - online/offline;
   - доставка сообщений;
   - realtime-обновления чатов.

6. **Media Service / Storage layer**
   - загрузка файлов;
   - хранение вложений;
   - доступ к медиа;
   - metadata по вложениям.

7. **Admin Panel Backend**
   - управление платформой;
   - просмотр жалоб;
   - модерация;
   - аудит действий администраторов.

## 6. Полное ТЗ

### 6.1. Назначение системы
SocketUp — это многопользовательская платформа обмена сообщениями и медиа-контентом, предназначенная для личного общения, групповой коммуникации, публикации контента в каналах и последующего расширения до production-ready messaging platform.

### 6.2. Основные сущности
Система должна поддерживать следующие сущности:
- пользователь;
- профиль пользователя;
- сессия устройства;
- личный чат;
- группа;
- канал;
- сообщение;
- вложение;
- голосовое сообщение;
- видеосообщение;
- статус доставки;
- статус прочтения;
- настройки приватности;
- системный администратор;
- жалоба (post-MVP);
- модерационное действие (частично post-MVP);
- запись аудита.

### 6.3. Роли

#### Роли внутри чатов
- `owner` — владелец;
- `admin` — администратор;
- `member` — участник.

#### Роли уровня платформы
- `system_admin` — системный администратор платформы;
- `user` — обычный пользователь.

### 6.4. Пользовательский аккаунт
Пользователь должен иметь возможность:
- зарегистрироваться по email;
- указать уникальный username;
- задать пароль;
- подтвердить email;
- входить с нескольких устройств;
- просматривать свои активные сессии;
- завершать отдельные сессии;
- завершать все остальные сессии.

#### Обязательные поля пользователя
- `username` — уникальный;
- `email` — уникальный, служебный;
- `password_hash` — внутреннее поле backend;
- `salt` — внутреннее поле backend;
- `phone` — необязательное / редактируемое;
- `first_name`;
- `last_name`;
- `middle_name`;
- `bio`;
- `avatar_url`;
- `last_seen`;
- `status`;
- `email_verified`;
- `phone_verified`;
- `is_admin`;
- `created_at`;
- `updated_at`.

### 6.5. Профиль и поиск пользователей
Система должна обеспечивать:
- поиск пользователя по `@username`;
- просмотр профиля;
- настройку видимости профиля;
- ограничение на начало чата с пользователем по privacy settings.

### 6.6. Личные чаты
Личный чат должен поддерживать:
- создание диалога между двумя пользователями;
- отправку текстовых сообщений;
- отправку вложений;
- отправку голосовых сообщений;
- отправку кружочков;
- reply;
- edit текста;
- delete у себя;
- delete у всех без ограничения по времени;
- forwarding с указанием автора;
- read/delivered statuses;
- typing indicator;
- online / last seen.

### 6.7. Группы
Группа должна поддерживать:
- создание группы;
- добавление и удаление участников;
- назначение ролей;
- изменение названия;
- изменение аватара;
- ban / mute / member management;
- pinned messages;
- историю сообщений;
- поиск сообщений внутри группы.

### 6.8. Каналы
Канал в MVP должен поддерживать:
- публикации от администраторов;
- комментарии к публикациям;
- управление правами публикации;
- публичную или закрытую модель доступа;
- хранение истории публикаций;
- прикрепление медиа и файлов.

### 6.9. Супергруппы
Супергруппы планируются как post-MVP и должны отличаться:
- большим лимитом участников;
- публичной ссылкой;
- темами / обсуждениями;
- расширенной организацией общения.

### 6.10. Сообщения
Сообщение должно поддерживать:
- текст;
- одно вложение;
- текст + вложение;
- reply_to;
- признак редактирования;
- soft delete;
- delete for self;
- delete for everyone;
- forwarding metadata;
- created_at / updated_at;
- delivery state;
- read state.

### 6.11. Голосовые сообщения
Голосовое сообщение должно иметь:
- ссылку на файл в объектном хранилище;
- длительность;
- waveform;
- размер файла;
- mime-type;
- sender_id;
- chat_id;
- timestamps.

### 6.12. Видеосообщения / кружочки
Кружочек должен иметь:
- ссылку на видеофайл;
- preview / thumbnail;
- длительность;
- размер;
- mime-type;
- sender_id;
- chat_id;
- timestamps.

### 6.13. Файлы и медиа
#### Требования к вложениям в MVP
- не более одного вложения на сообщение;
- размер вложения — до 5 МБ;
- хранение в MinIO / S3-compatible storage;
- в БД хранится metadata и ссылка на объект;
- обязательная mime/type validation;
- превью для изображений;
- поддержка файлов следующих типов:
  - image;
  - video;
  - audio;
  - document;
  - archive;
  - generic file.

### 6.14. Звонки
#### В MVP
- аудиозвонки;
- видеозвонки.

#### Post-MVP
- групповые звонки.

> На уровне архитектуры backend должен проектироваться с учётом будущей поддержки звонков уже сейчас.

### 6.15. Realtime
Система должна обеспечивать через WebSocket:
- мгновенную доставку сообщений;
- typing events;
- online/offline presence;
- read/delivered updates;
- обновление состояния чатов;
- доставку отложенных событий при следующем подключении пользователя.

#### Ограничения MVP
- retry/queue policy допускается упрощённой;
- гарантированная доставка realtime-событий может быть ограниченной;
- приоритет MVP — рабочий realtime pipeline.

### 6.16. Приватность
Пользователь должен иметь возможность настраивать:
- кто может написать первым;
- кто видит телефон;
- кто видит last seen;
- кто может добавлять в группы;
- кто может видеть профиль;
- кто может звонить.

Возможные уровни доступа:
- все;
- контакты;
- никто.

### 6.17. Push notifications
В MVP должны поддерживаться:
- push-уведомления для iOS-клиента.

Email notifications не являются обязательной частью MVP.

### 6.18. Жалобы, антиспам и модерация
Эти функции относятся к post-MVP:
- жалобы на пользователя;
- жалобы на сообщения;
- антиспам-механизмы;
- модерация платформы.

### 6.19. Административный контур
Система должна предусматривать:
- наличие web admin panel;
- роль системного администратора;
- аудит действий администратора;
- просмотр служебных данных платформы.

### 6.20. Нефункциональные требования
Система должна обладать следующими свойствами:
- масштабируемость;
- модульная архитектура;
- пригодность к дальнейшему росту;
- безопасное хранение учётных данных;
- работа с несколькими устройствами;
- отделение realtime, бизнес-логики и API-шлюза;
- возможность расширения по функционалу без полной переработки архитектуры.

### 6.21. Ограничения MVP
- максимум 1 вложение на сообщение;
- максимум 5 МБ на вложение;
- Android не входит в текущий roadmap;
- web client для обычных пользователей не входит в MVP;
- сложная модерация переносится на второй этап;
- супергруппы переносятся на второй этап.
